01

데이터 흐름

테스트 앱으로 보낸 요청은 로그가 된 다음 분석 결과로 저장됩니다.

1요청 생성

브라우저 또는 k6가 테스트 앱의 API를 호출합니다.

→
2로그 기록

FastAPI 미들웨어가 요청 정보와 응답 결과를 PostgreSQL request_logs에 남깁니다.

→
3구간 분석

Analyzer가 최근 구간을 집계해 규칙과 Isolation Forest로 검사합니다.

→
4결과 확인

대시보드에서 확인하고 분석 실행 결과는 analysis_results에 저장합니다.

역할 구분테스트 앱은 요청 로그를 쓰고 Analyzer는 그 로그를 읽어 분석 결과를 저장합니다. Prometheus 메트릭은 별도 경로이며 Isolation Forest 입력 데이터가 아닙니다.
02

두 가지 탐지 방식

명확한 임계치와 정상 패턴에서 벗어난 정도를 함께 살펴봅니다.

RULE BASED

규칙 기반 탐지

정해 둔 기준을 넘으면 경고합니다. 빠르고 근거를 설명하기 쉽습니다.

  • 선택 구간에서 IP별 요청이 20건 초과
  • 오류가 3건 이상이고 오류율이 50% 이상
  • 요청이 3건 이상이고 평균 응답 시간이 1,000ms 이상
요청 수가 60건 이상이거나 오류율이 80% 이상이면 심각도 높음으로 표시합니다.
UNSUPERVISED ML

Isolation Forest

정상으로 수집한 구간과 비교해 여러 특성의 조합이 드문 IP를 이상 후보로 표시합니다.

요청 수오류율평균 지연p95 지연경로 수
현재 설정: 트리 150개, contamination 0.05, random_state 42. IP별 최근 60초 데이터를 점수화합니다.
알아둘 점Isolation Forest는 외부 AI API나 라벨이 있는 지도학습 모델이 아닙니다. normal로 표시된 과거 로그로 기준선을 만들며, 표본이 20개보다 적으면 insufficient_data가 되어 규칙 탐지만 유효합니다.
03

정상 기준선 수집과 학습

Analyzer가 분석 요청을 받으면 기준선 데이터를 확인하고 필요하면 집계·학습 데이터를 갱신합니다.

  1. 1. k6에서 normal 프로필 실행21분 동안 낮은 빈도의 정상 요청을 보냅니다. 요청은 X-Traffic-Scenario: normal로 표시되어 DB에 저장됩니다.
  2. 2. 기준선 표본 확인분석 구간 직전 1일의 normal 요청을 클라이언트 IP별 분 단위로 집계합니다. 20개 이상의 분 단위 표본이 필요합니다.
  3. 3. 분석 요청으로 모델 평가최근 60초의 요청 특성을 계산해 기준선과 함께 Isolation Forest에 넣고 이상 점수와 판정을 만듭니다. 응답의 detector_metadata에서 학습 표본 수와 ready 상태를 확인합니다.
  4. 4. 정상·이상 시나리오 비교기준선 수집 후 normal_eval으로 오탐을 확인하고 burst·slow·error를 각각 실행해 탐지 결과를 비교합니다.
모델 캐시학습 집계는 Analyzer 프로세스 메모리에 캐시됩니다(기준선이 있으면 최대 5분, 아직 없으면 최대 1분). Pod가 재시작되면 DB 로그에서 다시 읽습니다. DB에 저장된 정상 기준선 로그는 유지됩니다.
04

k6 시나리오 실행

프로필별로 정상 기준선을 모으거나 이상 징후를 재현합니다.

프로필동작용도
normal/api에 5초 간격 요청, 21분정상 기준선 수집
normal_eval정상 요청 5분, 매 60초 분석 저장기준선 이후 여러 정상 창의 오탐 확인
burst_1/2/4/8/burst 초당 1·2·4·8건, 10초강도별 요청량 탐지 반응 비교
burst/burst 초당 8건, 10초기존 요청량 급증 시연
slow2초 지연 /slow 요청, 20초응답 지연 확인
error/error, 약 절반 HTTP 500오류 증가 확인
all시나리오를 짧게 함께 실행전시용 통합 시연

PowerShell 프로젝트 루트에서 실행합니다. 다음 프로필은 이전 Job 종료 후 60초 이상 간격을 두세요.

kubectl create configmap k6-run-profile --from-literal=RUN_PROFILE=normal -n smart-traffic --dry-run=client -o yaml | kubectl apply -f -
kubectl delete job k6-test -n smart-traffic --ignore-not-found
kubectl apply -f k8s/k6/k6.yaml
kubectl wait --for=condition=complete job/k6-test -n smart-traffic --timeout=25m
kubectl logs -n smart-traffic job/k6-test

다른 시나리오를 실행할 때는 첫 명령의 normal을 normal_eval, burst_1, burst_2, burst_4, burst_8, slow, error 또는 all로 바꿉니다. 스크립트를 수정했다면 README의 ConfigMap 갱신 명령도 먼저 실행하세요.

05

접속과 API 사용

Analyzer는 Kubernetes 내부 서비스로 실행되므로 로컬에서 볼 때 포트포워딩을 엽니다.

kubectl port-forward -n smart-traffic svc/traffic-analyzer-service 9000:9000
http://localhost:9000/dashboard실시간 대시보드
http://localhost:9000/guide이 사용 가이드
GET /traffic/summary?window_seconds=60최근 구간 요약만 조회, 저장하지 않음
POST /analyze?window_seconds=60분석 실행 후 결과를 DB에 저장
GET /analyses?limit=20최근 저장 결과 목록
GET /analyses/{id}저장된 결과 한 건 조회
curl -X POST "http://localhost:9000/analyze?window_seconds=60"
curl "http://localhost:9000/analyses?limit=20"
저장 위치요청 로그는 PostgreSQL request_logs, 분석 실행 결과는 analysis_results에 저장됩니다. 대시보드는 포트포워딩 터미널이 실행 중인 동안 접속할 수 있습니다.
