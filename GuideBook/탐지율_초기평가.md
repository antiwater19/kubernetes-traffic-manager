# Isolation Forest 초기 탐지율 평가

## 정상 오탐 및 Burst 지속 시간 평가 (2026-10-24 KST)

정상 트래픽은 서로 다른 k6 Job으로 반복 실행했다. 먼저 30초 실행 5회(ID 82~86)를 확인했지만 각 분석 창에는 정상 요청 6건만 들어가 기준선의 1분 IP-분 표본과 비교 조건이 달랐다. 이 결과는 별도로 남기고, 60초 정상 실행 5회(ID 98~102)를 추가해 60초 분석 창과 같은 길이로 재평가했다. 두 묶음 모두 모델은 `ready`였고, 실행 사이에는 분석 창을 분리하도록 대기했다.

| 정상 프로필 | 분석 요청 수 | Isolation Forest 오탐 | 규칙 탐지 | 통합 결과 |
|---|---:|---:|---:|---|
| 30초 실행 (ID 82~86) | 매회 6건 | 5/5 (100%) | 0/5 | 5/5 이상 |
| 60초 실행 (ID 98~102) | 매회 11건 | 0/5 (0%) | 0/5 | 0/5 정상 |

30초 실행은 매회 Isolation Forest가 이상으로 표시했지만, 분석 창의 절반만 정상 부하를 보내 기준선의 분 단위 집계와 맞지 않았다. 60초 실행은 다섯 번 모두 이상이 없었다. 따라서 30초 결과를 운영 오탐률로 해석하지 않고, 60초로 조건을 맞춘 결과도 표본 5개에 대한 초기 측정으로 한정한다.

Burst는 초당 8건으로 고정하고 지속 시간을 10초·30초·60초로 바꿔 각각 세 번씩 평가했다. 분석 창 사이 간격이 짧아 이전 burst와 섞인 ID 88, 89는 제외했다. 유효한 세 반복은 모두 단일 지속 시간의 트래픽만 포함했다.

| Burst 지속 시간 | 분석 요청 수 | Isolation Forest 탐지 | 규칙 기반 탐지 | 통합 결과 |
|---|---:|---:|---:|---:|
| 10초 (ID 92, 95, 97) | 80~81건 | 0/3 (0%) | 3/3 (100%) | 3/3 이상 |
| 30초 (ID 87, 91, 94) | 240~241건 | 1/3 (33.3%) | 3/3 (100%) | 3/3 이상 |
| 60초 (ID 90, 93, 96) | 매회 481건 | 1/3 (33.3%) | 3/3 (100%) | 3/3 이상 |

지속 시간이 길수록 Isolation Forest 탐지율이 계속 오르는 패턴은 이 표본에서 확인되지 않았다. 10초는 0/3, 30초와 60초는 각각 1/3이었고, 세 지속 시간 모두 규칙은 전부 탐지했다. burst 결과에서 모델 상태는 `ready`, 학습 표본은 30개였다. 정상 60초 평가의 학습 표본은 30~39개였다.

모든 k6 HTTP 요청은 실패율 0%였고 분석 결과는 `analysis_results`에 저장됐다. 현재 rolling 24시간 정상 IP-분 기준선은 40개다. 오탐률과 탐지율은 각각 다섯 번 또는 세 번의 독립 실행에 대한 관찰값이며, 일반 성능으로 단정하지 않는다.

### 점수와 입력 특성 비교

분석 결과의 `client_summaries[].isolation_forest`에 정상으로 판정된 클라이언트의 점수도 저장되어 있어, 이를 기준으로 비교했다. `decision_score`가 0보다 작으면 이상, 0 이상이면 정상이다. 모든 비교군에서 오류율은 0%, 경로 수는 1개였다.

| 실행 조건 | 요청 수 | 평균 지연 | p95 지연 | 점수 범위 | 이상 판정 |
|---|---:|---:|---:|---:|---:|
| 정상 30초 | 6 | 0.45~1.68ms | 0.49~3.87ms | -0.029378~-0.002574 | 5/5 |
| 정상 60초 | 11 | 0.46~0.50ms | 0.56~0.79ms | 0.117371~0.161628 | 0/5 |
| burst 10초 | 80~81 | 0.47~0.49ms | 0.58~0.62ms | 0.010377~0.016300 | 0/3 |
| burst 30초 | 240~241 | 0.45~0.50ms | 0.56~0.66ms | -0.004355~0.007673 | 1/3 |
| burst 60초 | 481 | 0.47~0.51ms | 0.64~0.68ms | -0.002837~0.005435 | 1/3 |

실험 당시 정상 기준선은 오류율 0%, 경로 1개였고, 요청 수는 ID 82 평가 시 최소 6·중앙값 12·최대 12, ID 87 평가 시 최소 1·중앙값 12·최대 12였다. 정상 30초 실행의 6건은 기준선 최저값과 같지만 전형적인 12건 표본보다 적었다. 60초 정상 실행의 11건은 기준선 중앙값 12에 가까웠다. 따라서 30초에서 나온 오탐은 분석창 절반만 부하를 준 조건 차이와 낮은 요청량에 민감한 현재 모델의 영향을 받았다고 볼 수 있다. 동일 길이의 정상 60초 실행에서는 점수가 모두 충분히 양수였다.

Burst는 요청 수만 기준선의 최대 12건을 크게 넘었고 평균·p95 지연은 정상 표본과 비슷했다. 그런데 burst 점수는 대부분 0 근처의 좁은 범위에 있었고, 같은 지속 시간의 반복에서도 부호가 바뀌었다. 현재 코드가 Isolation Forest를 학습할 때 과거 정상 표본뿐 아니라 이번에 점수화할 `current` 행도 함께 `fit`에 넣고(`detector.py`의 `np.vstack([training, current])`), `contamination=0.05`로 그 합친 자료에서 판정 경계를 다시 정하기 때문이다. 단일 클라이언트만 점수화하는 실험에서는 현재 표본 하나가 매 실행의 경계 계산에도 참여한다. 작은 기준선과 결합해 결과가 반복마다 흔들릴 수 있다. 규칙의 20건 초과 기준은 이 burst 요청량을 매번 잡았지만, Isolation Forest 단독 판정은 안정적이지 않았다.

metadata의 `decision_threshold`는 scikit-learn `offset_` 원점수이고, `client_summaries`의 `decision_score`는 offset을 적용한 점수다. 둘은 직접 비교하는 값이 아니며, 현재 `predict` 결과는 조정 점수가 0보다 작은지로 판정한다.

## Burst 강도별 재현성 평가 (2026-10-24 KST)

rolling 24시간 기준선이 최소 20개 표본을 유지하는 것을 확인했다. 첫 평가 묶음(ID 62~69)에서 강도별 2회 결과를 얻은 뒤, k6 `burst_1`, `burst_2`, `burst_4`, `burst_8`을 각각 3회씩 추가 실행했다(ID 70~81). 추가 실행은 강도 순서를 섞었고, 각 Job 완료 후 65초 대기해 분석 시간창끼리 트래픽이 섞이지 않도록 했다. 모든 저장 결과에서 모델 상태는 `ready`였으며 학습 표본은 22~28개였다. 평가가 끝난 뒤 rolling 24시간 정상 기준선은 22개였다.

| 프로필 | 요청 강도 | 요청 수 범위 | Isolation Forest | 규칙 기반 | 통합 결과 |
|---|---:|---:|---:|---:|---|
| `burst_1` (ID 62, 66, 70, 75, 78) | 초당 1건 | 10~11 | 1/5 (20%) | 0/5 (0%) | 1/5 이상 |
| `burst_2` (ID 63, 67, 72, 74, 79) | 초당 2건 | 20~21 | 3/5 (60%) | 3/5 (60%) | 5/5 이상 |
| `burst_4` (ID 64, 68, 71, 77, 80) | 초당 4건 | 40~41 | 3/5 (60%) | 5/5 (100%) | 5/5 이상 |
| `burst_8` (ID 65, 69, 73, 76, 81) | 초당 8건 | 80~81 | 5/5 (100%) | 5/5 (100%) | 5/5 이상 |

## 재현성 평가 해석

- 가장 높은 강도인 `burst_8`은 Isolation Forest가 5회 모두 이상으로 판정했다. 이번 테스트 조건에서는 재현됐지만 표본이 5회뿐이라 일반 성능으로 확대 해석하지 않는다.
- `burst_1`은 5회 중 1회, `burst_2`와 `burst_4`는 각각 5회 중 3회 Isolation Forest가 이상으로 판정했다. 이전 두 차례에서 `burst_1`은 0/2, `burst_2`와 `burst_4`는 0/2였으므로, 초기 2회만으로 본 결과는 안정적이지 않았다.
- 규칙 기반 탐지는 `burst_2`에서 요청 수가 21일 때 이상으로 판정하고, 20일 때는 판정하지 않았다. `burst_4`와 `burst_8`은 전부 규칙 기반 탐지됐다.
- 20건 기준이 포함된 `burst_2`에서도 요청 수 20인 창은 IF만 이상으로 판정했다. 따라서 통합 결과와 Isolation Forest 결과를 구분해서 해석해야 한다.
- k6 HTTP 요청은 모든 실행에서 실패 없이 끝났고, 12개 추가 분석 결과는 PostgreSQL `analysis_results`에 ID 70~81로 저장됐다. 최종 k6 Job은 `Complete`다.
- 이 평가는 같은 k6 프로필과 같은 클러스터를 사용한 반복 실험이다. 독립 환경, 정상 트래픽에서의 오탐 재현성, 장시간 부하, 다른 시간대·지속 시간은 아직 평가하지 않았다. 지금 결과로 정확한 모델 임계점이나 운영 환경 탐지율을 단정할 수 없다.

## 신규 기준선 및 시나리오 평가 (2026-10-23 KST)

먼저 k6 `normal` 프로필을 21분 실행해 정상 기준선을 다시 수집했다. 분석 결과 ID 40에서 모델은 `ready`, 학습 표본은 21개였다. 기존 `normal_eval` 분석 창 6개(ID 41~45 포함)에 이번에 추가한 창 5개(ID 52~56)를 합쳐 정상 평가 창은 11개가 됐다. 새 창 5개는 모두 모델 `ready`, 학습 표본 28개였고 이상을 탐지하지 않았다. `normal_eval`은 5분간 정상 부하를 주면서 분당 한 번 분석하고 마지막 결과도 저장하도록 개선했다. burst·slow·error는 각 두 번씩 실행했고, 시나리오 전환 사이에는 60초 이상 간격을 두었다.

| 시나리오 | 신규 평가 창 | Isolation Forest 탐지 | IF 탐지율 / 오탐률 | 통합 탐지 |
|---|---:|---:|---:|---:|
| 정상 | 11 | 0 | 오탐 0/11 (0%) | 0/11 |
| burst | 2 (81, 84건) | 0 | 0/2 (0%) | 2/2 (100%) |
| slow | 2 (각 20건) | 2 | 2/2 (100%) | 2/2 (100%) |
| error | 2 (각 80건) | 2 | 2/2 (100%) | 2/2 (100%) |

추가 실행 ID 57(burst)은 요청 84건을 통합 탐지했지만 Isolation Forest의 `anomalies`는 0이었다. ID 58(slow)은 20건 요청에서 모델 이상 1건, ID 59(error)는 80건 요청에서 모델 이상 1건을 기록했다. 이전 신규 실행 ID 46~48과 합쳐 각 이상 시나리오의 신규 반복은 두 번뿐이다. 결과는 초기 관찰로 해석하고 일반적인 탐지율로 일반화하지 않는다.

## 평가 범위

2026년 10월 13일~18일에 PostgreSQL `analysis_results`와 `request_logs`에 저장된 결과를 대조했다. 각 분석 결과의 분석 시간창에 기록된 `scenario`를 정답 라벨로 사용했고, 둘 이상의 시나리오가 섞인 시간창은 제외했다. 모델이 준비된(`detector_metadata.status = ready`) 분석 중 시나리오별 트래픽이 실제로 발생한 시간창만 집계했다.

- 정상: `normal` 요청 8건 이상
- burst: `burst` 요청 20건 이상
- slow: `slow` 요청 5건 이상
- error: `error` 요청 10건 이상
- Isolation Forest 적중: `detector_metadata.anomalies > 0`
- 통합 탐지 적중: 저장 결과의 `status = abnormal` (규칙 + Isolation Forest)

## 해석과 한계

- 기존 데이터에서는 burst를 규칙 기준(60초 요청 20건 초과)으로 9/9 탐지했지만, Isolation Forest 단독으로는 5/9만 탐지했다. 새 기준선 평가에서도 burst 2건 모두 규칙 탐지됐고 Isolation Forest는 0/2였다. 현재 burst 시나리오는 규칙이 더 안정적으로 잡고 있다.
- slow와 error는 각 4/4 탐지됐지만 표본이 4개뿐이므로 일반적인 성능으로 단정할 수 없다.
- 새 기준선의 정상 오탐 0/11은 평가한 11개 창에서 오탐이 없었다는 뜻이다. 같은 k6 실행에서 이어진 5개 창을 포함하고 있으며, 실제 오탐률이 0%라고 결론 내리기에는 독립 실행과 트래픽 조건의 다양성이 부족하다.
- 기존 결과 표는 2026년 10월 13~18일의 DB 기록에서 계산한 과거 기준이다. 위의 10월 23일 표는 기준선을 다시 수집한 뒤 별도로 수행한 신규 측정이며, 두 평가 집합은 구분해서 해석해야 한다.
- 이 결과는 분석 시간창 단위의 초기 비교다. 운영 환경의 일반화 성능을 주장하기 위한 충분한 독립 반복이나 별도 검증 데이터는 아니다.

## 후속 평가 계획

기준선은 rolling 24시간 안에 최소 20개의 정상 IP-분 표본을 유지하고, 서로 다른 시나리오가 섞인 분석 창은 평가에서 제외한다. 최신 v16 재평가와 후속 특성 검토 내용은 아래에 기록한다.

## 다음 개선 적용: 기준선 고정 학습

이전 구현은 과거 정상 기준선과 현재 분석 배치를 함께 Isolation Forest에 넣어 학습했다. 따라서 burst 트래픽 자체가 분할 경계와 `contamination`에 따른 임계값에 영향을 줄 수 있었다. 이번 변경부터 모델은 과거 정상 기준선(`training`)으로만 학습하고 최근 트래픽(`current`)은 그 모델에 점수화한다. API의 `detector_metadata`에는 `fit_scope = historical_normal_baseline` 및 `scoring_batch_included_in_training = false`가 표시된다.

analyzer `v16`을 Docker Hub에 push하고 Kubernetes `traffic-analyzer` 배포에 적용했다. 배포 rollout은 성공했고 Pod가 `1/1 Running`임을 확인했다. 적용 후 재평가 결과는 아래에 별도 집계했으며, 앞의 표들은 v16 적용 전 측정치다.

|---|---|---|---|
| 정상 60초, 약 11건 | IF 오탐 0/5, 점수 +0.117371~+0.161628 | IF 오탐 0/5, 점수 +0.050464~+0.222523 | 0/5 |
| burst 60초, 약 480건 | IF 탐지 1/3, 점수 -0.002837~+0.005435 | IF 탐지 0/3, 점수 +0.219684~+0.276125 | 3/3 |

신규 분석 ID는 정상 `103, 105–108`, burst `104, 109–110`이다. v16 정상 5회 모두 요청 11건, 오류율 0%, 경로 1개였고 오탐이 없었다. 평균 지연은 0.47–0.72ms, p95는 0.67–1.78ms였다. burst는 480–481건, 오류율 0%, 경로 1개였고 평균 지연은 0.48–0.58ms, p95는 0.62–0.87ms였다. 모든 burst에서 요청 수 규칙(60초 20건 초과)이 탐지했고, Isolation Forest는 3회 모두 정상으로 판정했다. 점수는 양수일수록 정상 판정 쪽이며 음수일 때 이상 판정이다.

### 해석

- 정상 오탐은 두 평가 모두 0/5로 유지됐다.
- burst의 IF 단독 탐지는 적용 전 1/3에서 v16 0/3으로 떨어졌다. 통합 API는 규칙으로 각각 3/3을 잡았다.
- v16에서 오류율과 경로 수는 두 조건이 같고 지연 시간도 상당히 겹쳤지만, 요청 수는 정상 11건과 burst 약 480건으로 크게 달랐다. 그런데 burst 점수가 정상보다 더 큰 양수였다. 이 측정에서는 기준선만으로 학습하도록 바꾼 것이 burst 탐지 문제를 해결하지 못했다. 요청 수의 긴 꼬리와 특성별 규모 차이가 영향을 주는지 확인하기 위해 로그 변환·표준화와 임계값 보정을 별도 비교해야 한다.
- 적용 전후의 점수 범위는 그대로 학습한 모델끼리의 직접 비교가 아니다. 학습 표본 수도 기존 30–39개에서 v16 평가 중 41–49개로 달라졌다. 반복 수는 맞췄지만 각 시나리오 표본은 5개와 3개뿐이므로 초기 비교로만 해석한다.

이번 실행 후 `k6-run-profile`은 이전 설정인 `burst_8`로 복원했다. 완료된 결과는 `analysis_results`에 남아 있다.

## 요청 수 변환·스케일링 및 임계값 검토

현재 `_feature_row()`는 `request_count`, `error_rate`, 평균·p95 지연, `unique_paths`를 원래 단위로 반환한다. v16의 저장 결과 점수를 오름차순으로 보면 정상 5개는 `+0.050464, +0.097894, +0.189814, +0.206992, +0.222523`, burst 3개는 `+0.219684, +0.233257, +0.276125`다. IF의 기본 판정은 `decision_score < 0`일 때 이상이다.

### 임계값만 바꾸는 경우

- 기본 임계값 0에서는 정상 오탐 0/5지만 burst 탐지도 0/3이다.
- 정상 표본에서 오탐을 하나도 허용하지 않으려면 낮은 점수를 이상으로 보는 임계값은 최소 정상 점수(+0.050464) 이하로 둬야 한다. 이 경우 burst는 하나도 탐지되지 않는다.
- 세 burst를 모두 탐지하려면 임계값을 가장 높은 burst 점수(+0.276125)보다 높여야 한다. 그러면 정상 5개도 모두 이상으로 판정된다.
- 따라서 현재 표본 순위에서는 기본 IF 방향(낮은 점수 = 이상)으로 임계값 하나만 조정해 정상과 burst를 분리할 수 없다. 임계값은 점수 순위를 바꾸지 못한다. v16의 8개 표본만으로 임계값을 튜닝하면 정상 오탐을 크게 늘릴 위험이 있다.
- 점수가 높은 쪽을 이상으로 뒤집으면 이번 작은 표본에서는 burst 2/3, 정상 오탐 0/5가 되지만, IF 점수의 의미를 뒤집고 8개 표본에 과적합하므로 운영 판정으로 채택하지 않는다.

### 변환·스케일링 후보

- 단순 `StandardScaler`·`MinMaxScaler` 같은 feature별 선형 스케일링은 우선순위가 낮다. Isolation Forest는 각 분할에서 feature 범위 내 임의 위치를 고르므로, 선형 스케일링은 분할 위치의 상대 비율을 보존하고 트리 구조와 점수 순위를 거의 바꾸지 않는다.
- `log1p(request_count)`는 검토할 가치가 있다. 정상 약 11건과 burst 약 480건의 차이를 압축하면서 요청 수 긴 꼬리의 분할 구조를 바꿀 수 있다. 다만 이번 DB에는 원래 입력과 점수만 저장돼 있고 전체 학습 행렬이 공개되지 않아, 변환 적용 후 점수를 이 기록만으로 재계산하지는 않았다.
- 평가용 다음 후보는 `raw`와 `log1p(request_count)` 두 가지로 한정하고, 나머지 네 특성·모델·표본을 고정해 비교한다. 별도 정상 검증 점수로 허용 오탐률에 맞는 임계값을 정한 다음 이상 시나리오를 평가해야 한다. `contamination=0.05`는 학습 표본의 점수 분포에서 경계를 정할 뿐, 새 트래픽의 오탐률을 5%로 보장하지 않는다.

### 검토 범위와 권고

이번 검토는 v16의 정상 5개와 burst 3개 저장 결과를 이용한 임계값 순위 분석이다. 변환별 오프라인 재학습·점수 비교는 수행하지 않았다. 현재 Docker Desktop Kubernetes API가 `kubernetes.docker.internal` 이름을 찾지 못해 기준선 전체를 조회할 수 없었기 때문이다. 다음 개선은 선형 스케일링이나 `contamination` 조정부터 하는 것보다, 고정된 데이터셋에서 `raw`와 `log1p(request_count)`를 같은 정상 홀드아웃 및 burst 홀드아웃으로 비교하는 실험이 적절하다. 기존 요청 수 규칙은 이 비교 동안 유지한다.
